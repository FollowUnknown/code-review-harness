# v1.4.0 业务场景与影响分析

> 日期: 2026-05-09
> 目的: 在实施前明确每个改造点对应的真实业务场景、优化效果和影响范围

---

## 一、核心业务场景对照

### 场景 1: 后端负责人评审一个需求（改动 7-8 个后端项目）

**角色**: 后端技术负责人
**频率**: 每天至少 1-2 次

#### 改造前（现状）

```
1. 打开 /local-review，选择项目 "bpms-runtime"，选分支，开始评审
2. 等 2-3 分钟，拿到报告
3. 切换项目 "do1cloud-form"，重新评审
4. 等 2-3 分钟，拿到报告
5. 切换项目 "bpms-component"，重新评审
6. ...重复 5-6 次
7. 手动汇总所有项目的报告，整理出一份需求级的问题清单
8. 把问题反馈给各个开发者
```

**痛点**:
- 操作 7-8 次，每次都要选项目、选分支、等评审
- 无法看到跨项目的关联改动（如 bpms-component 改了接口，bpms-runtime 调用方受影响）
- 知识注入不完整：当前只注入当前项目的知识，不知道其他项目也有改动
- 汇总报告靠人工，容易漏掉跨项目问题

#### 改造后

```
1. 打开 /requirement-review，选择产品线"七巧"，选分支
2. 系统预扫描: 显示所有有 diff 的项目列表
   - bpms-runtime: 12 个文件
   - do1cloud-form: 5 个文件
   - bpms-component: 3 个文件
   - ...共 7 个项目
3. 确认排除不需要评审的项目（如只改了注释的项目）
4. 点"开始评审"，系统自动：
   - 按技术栈分组（这里全是 Java 后端，一组）
   - 7 个项目并行扫描 diff
   - 每个项目独立评审（共享基础知识和产品线知识）
   - bpms-component 改了 ServiceFacade.java → 系统提示 "下游 bpms-runtime, do1cloud-form 依赖此项目"
5. 5-8 分钟后拿到一份合并报告：
   - 总评: 3.8/5, 7 个问题, 1 个 Critical
   - 跨项目影响: bpms-component 接口签名变更影响 2 个下游
   - 按项目展开: 每个项目的问题列表
```

**优化点**:
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 操作次数 | 7-8 次 | 1 次 |
| 等待时间 | 7-8 × 3min = 21-24min | 5-8min（并行） |
| 跨项目关联 | 看不到 | 自动检测依赖影响 |
| 报告汇总 | 人工整理 | 自动合并 |
| 知识覆盖 | 只看当前项目知识 | 基础 + 产品线 + 跨项目 + 项目级全注入 |

### 场景 2: 前后端联合需求评审（后端 + 前端同时开发）

**角色**: 后端负责人（兼看前端）或各自负责人
**频率**: 每周 2-3 次

#### 改造前

```
后端评审: 重复场景 1 的流程，7-8 个项目逐个评审
前端评审: 单独对 do1cloud-qiqiao-console-web 评审
前后端对照: 人工比对后端接口改动和前端调用是否一致
```

**痛点**:
- 前后端评审完全割裂，看不出 API 不一致
- 后端改了返回字段名（userId → userNo），前端没人知道
- 没有前后端 API 契约知识，评审时无法校验一致性

#### 改造后

```
1. 选择产品线"七巧"，选分支
2. 预扫描显示:
   - [Java 后端] bpms-runtime: 12 文件, do1cloud-form: 5 文件, ...
   - [Vue 前端] do1cloud-qiqiao-console-web: 3 文件
3. 系统按技术栈自动分组:
   - Java 后端组: 7 个项目
   - Vue 前端组: 1 个项目
4. 各组独立评审:
   - Java 组: 用 Java 后端维度集 (9 个维度)
   - Vue 组: 用 Vue 前端维度集 (12 个维度)
   - 两组都注入 Layer 2 前后端逻辑知识（API 契约）
5. 合并为一份产品级报告:
   - Java 组评分: 3.8/5
   - Vue 组评分: 4.2/5
   - 跨技术栈问题: "后端用户列表接口返回 userId，前端使用 id 调用"
```

**优化点**:
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 前后端对照 | 人工比对 | 自动注入 API 契约知识校验 |
| 维度集 | 固定一套 | 按技术栈自动切换 |
| 跨技术栈问题 | 发现不了 | 自动标注 |
| 操作流程 | 前后端分开操作 | 一次操作搞定 |

### 场景 3: 新项目接入评审系统

**角色**: 技术负责人
**频率**: 偶尔（新项目上线时）

#### 改造前

```
1. 在 /settings 的 repo mapping 里手动添加每个项目
2. 逐个输入项目名和本地路径
3. 没有产品线归属，无法与其他项目关联
4. 知识库需要手动为每个项目创建基础规则
5. 新项目评审时没有产品线级别的共享知识
```

**痛点**:
- 七巧 23 个后端 + 7 个前端，手动逐个配置太慢
- 新项目没有历史知识，评审质量低
- 无法复用同产品线其他项目的知识

#### 改造后

```
1. 打开 /product-lines，选择"七巧"产品线
2. 点击"快速导入"，输入目录前缀 /Users/tzknow/.../qiqiao/backend/
3. 系统自动扫描子目录，发现 23 个后端项目
4. 批量创建 repo_mapping，自动标记 tech_stack = "java-backend"
5. 新项目自动继承:
   - Layer 0: Java 基础安全规范、编码规范
   - Layer 1: 七巧业务规则、产品名词
   - Layer 2: 前后端 API 契约
   - 只有 Layer 3（项目级知识）需要积累
```

**优化点**:
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 接入方式 | 逐个手动添加 | 目录前缀批量导入 |
| 知识起点 | 空白 | 自动继承产品线三层共享知识 |
| 技术栈标记 | 无 | 自动推断或手动指定 |
| 首次评审质量 | 低（无知识） | 中等（有基础和产品线知识兜底） |

### 场景 4: 改动被依赖的公共组件

**角色**: 后端开发者
**频率**: 每周 1-2 次

#### 改造前

```
1. 开发者改了 bpms-component 的 ServiceFacade.java
2. 提交代码，负责人评审 bpms-component
3. 评审报告只看 bpms-component 内部的问题
4. 没有人意识到 bpms-runtime 和 do1cloud-form 依赖这个接口
5. 发布后下游项目报错: 方法签名不兼容
```

#### 改造后

```
1. 开发者改了 bpms-component 的 ServiceFacade.java
2. 负责人在需求评审中评审 bpms-component
3. 系统自动检测: ServiceFacade.java 属于公共 API
4. prompt 注入依赖提示:
   "本次改动涉及 bpms-component。以下项目依赖 bpms-component:
    - bpms-runtime (compile 依赖)
    - do1cloud-form (compile 依赖)
    改动文件: ServiceFacade.java
    请检查: 1. 接口签名向后兼容  2. DTO 字段只增不删  3. 是否需通知下游"
5. LLM 基于此提示给出更精准的评审意见
6. 报告中标注: [跨项目影响] bpms-runtime, do1cloud-form
```

**优化点**:
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 依赖感知 | 无 | 自动检测并提示 |
| 下游影响 | 发布后才发现 | 评审时预警 |
| LLM 审查范围 | 只看当前文件 | 结合依赖信息审查兼容性 |
| 问题标注 | 无跨项目标记 | 明确标注影响的下游项目 |

## 二、知识库改造的具体影响

### 改造前知识库现状

| 类别 | 数量 | 占比 | 问题 |
|------|------|------|------|
| qiqiao 项目知识 | 168 条 | 45% | 前后端混在一起，无法区分产品级 vs 项目级 |
| shared 通用知识 | 6 条 | 1.6% | 只有前端规则，缺少后端安全/性能规则 |
| java-backend | 20 条 | 5.4% | 作为 project 字段存储，与产品线知识无法区分 |
| vue-frontend | 少量 | — | 散落在各项目中，无统一管理 |
| 跨前后端知识 | 0 条 | 0% | **完全没有** API 契约、字段映射等知识 |

### 改造后知识分层效果

```
Layer 0 (foundation): ~30 条
  - "禁止硬编码密钥" (from shared)
  - "SQL 必须参数化" (from shared)
  - "Java Service 类必须有事务注解" (from java-backend)
  - "Vue 组件必须有 name 属性" (from vue-frontend)
  → 所有项目评审时都注入，与技术栈关联

Layer 1 (product): ~50 条
  - "七巧表单字段命名规范" (from qiqiao 产品级)
  - "工作流状态机规则" (from qiqiao 产品级)
  - "表单校验统一用 xx 规则" (from qiqiao 产品级)
  → 七巧所有项目评审时都注入

Layer 2 (integration): ~20 条（需新建）
  - "用户列表接口返回 userId 而非 id"
  - "日期格式统一 yyyy-MM-dd"
  - "分页接口返回 {list, total, page, size}"
  → 前后端评审时都注入

Layer 3 (project): ~100 条
  - "bpms-runtime 的定时任务必须在 xx 表注册"
  - "do1cloud-form 的模板引擎限制 xx"
  → 只在对应项目评审时注入
```

### 合并评审的知识效率

**单项目评审**（改造前后对比）:
| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 知识来源 | 隐式（靠 project 名字匹配） | 显式（scope_level 字段） |
| 跨项目知识 | 看不到（除非恰好同名） | 产品线级知识自动注入 |
| API 契约 | 无 | Layer 2 注入 |
| 知识预算 | 固定 4000 tokens | 分层预算，优先级明确 |

**合并评审**（新增能力）:
| 维度 | 效果 |
|------|------|
| 共享知识加载 | Layer 0 + 1 + 2 只加载一次，缓存复用 |
| 首项目 | 加载全量知识 3600 tokens |
| 后续项目 | 只加载项目级知识 1500 tokens |
| 8 项目评审 | 节省 ~60% 知识加载量 |

### 3.3 数据迁移影响

**知识库迁移预览**（基于当前 372 条知识）:

```
scope_level = 'foundation':
  - project = 'shared' (6 条) → 自动迁移
  - project = 'java-backend' (20 条) → 自动迁移
  - project = 'vue-frontend' (少量) → 自动迁移
  预计: ~30 条

scope_level = 'product':
  - project = 'qiqiao' 且内容为产品级规则 → 需人工确认
  - project = 'qiqiao' 且内容为前后端契约 → 归入 integration
  预计: ~50 条（需确认边界）

scope_level = 'integration':
  - 需从 qiqiao 项目知识中分离出 API 契约类条目
  预计: ~0 条（当前没有，需新建）

scope_level = 'project':
  - 具体项目名（do1cloud-form 等）的条目
  - 剩余所有条目
  预计: ~290 条
```

**迁移策略**:
1. 先自动标注 foundation 和 project 级（规则清晰）
2. product 级提供预览，用户确认后执行
3. integration 级暂不迁移（当前无数据，后续手工录入）
4. 迁移后运行一次单项目评审，对比结果是否一致

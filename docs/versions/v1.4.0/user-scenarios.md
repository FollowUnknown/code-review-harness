## 场景 1: 多项目需求评审

### 背景
后端负责人评审一个需求时，通常涉及 7-8 个后端项目。改造前需要逐个项目选择、分支、等待评审（每次约 3 分钟），然后人工汇总报告。跨项目关联改动（如 bpms-component 改了接口，bpms-runtime 是调用方）完全看不到。

### 操作流程
1. 打开 `/requirement-review`，选择产品线"七巧"和源/目标分支
2. 点击"预览变更"，2-3 秒后系统列出所有有 diff 的项目（文件数、增删行数）
3. 勾选/排除需要评审的项目（如排除仅改注释的），点击"开始评审"
4. 系统自动按技术栈分组、并行扫描、逐项目评审（共享基础+产品线知识只加载一次）
5. 5-8 分钟后获得合并报告

### 输出
- 一份产品级合并报告，总评分 + 问题统计 + Critical 标记
- 跨项目影响面板：如 bpms-component 的 ServiceFacade 签名变更影响下游 3 个项目
- 按项目 Tab 展开，每个项目独立评分和问题列表
- 操作次数从 7-8 次降至 1 次，等待时间从 21-24min 降至 5-8min（并行处理）

## 场景 2: 前后端联合评审

### 背景
需求同时涉及后端（Java 项目组）和前端（Vue 项目）。改造前前后端评审完全割裂：后端逐个评审 7 个项目，前端单独评审，人工比对 API 一致性。后端改了返回字段名，前端无人知晓，直到联调或上线才发现。

### 操作流程
1. 同场景 1，选择产品线和分支后预览变更
2. 系统自动按技术栈分组：Java 后端组（7 项目）、Vue 前端组（1 项目）
3. 各组用独立维度集评审：Java 组用 9 个后端维度，Vue 组用 12 个前端维度
4. 两组均注入 Layer 2 前后端逻辑知识（API 契约、字段映射等）

### 输出
- 一份产品级报告，含 Java 后端组评分和 Vue 前端组评分（分 Tab 展示）
- 跨技术栈问题段落：如"后端 getUserList 返回 {userId, name}，前端使用 {id, name}"
- 前后端从分开操作 2 次变成 1 次操作，API 不一致从"发现不了"变成"自动标注"

## 场景 3: 产品线管理与新项目接入

### 背景
七巧产品线有 23 个后端 + 7 个前端项目。改造前需在 `/settings` 逐个手动输入项目名和路径，技术栈无标记，产品线无归属，新项目评审时几乎没有知识（仅 shared 6 条通用规则），评审质量很低。

### 操作流程
1. 打开 `/product-lines`，选择产品线"七巧"
2. 点击"快速导入"，输入目录前缀（如 `/Users/.../qiqiao/backend/`）
3. 系统扫描子目录，发现所有 Git 仓库，自动推断技术栈
4. 批量创建 repo_mapping，关联产品线，标记 tech_stack
5. 新项目自动继承 Layer 0（基础安全/编码规范）、Layer 1（产品业务规则）、Layer 2（API 契约）

### 输出
- 23 个项目一键导入（原需逐个手配，每项目约 30 分钟）
- 新项目首次评审知识覆盖从 ~5% 提升至 ~60%（foundation + product + integration 兜底）
- 产品线页面可查看所有项目和依赖关系，支持手动编辑路径并 verify

## 场景 4: 依赖感知与公共组件改动

### 背景
开发者改了 bpms-component 的公共 API（如 ServiceFacade.java），评审时只看当前项目内部问题，没人意识到 bpms-runtime、do1cloud-form 等项目依赖此接口。发布后下游项目报错才暴露不兼容。

### 操作流程
1. 在需求评审上下文中，系统扫描 pom.xml 识别 compile 依赖关系
2. 当 bpms-component 的 diff 涉及公共 API 文件时，prompt 自动注入下游信息：
   - "以下项目依赖 bpms-component: bpms-runtime, do1cloud-form, do1cloud-auth"
   - "请检查：接口签名向后兼容、DTO 字段只增不删、是否需通知下游"
3. LLM 结合依赖信息做出更精准的兼容性审查
4. 报告中标注 crossProjectImpact 字段，明确影响范围

### 输出
- 破坏性变更（如方法签名改变）标注 [HIGH] + 跨项目影响
- 向后兼容变更（如 DTO 新增字段）标注 [MEDIUM]，说明不影响现有逻辑
- 依赖关系支持 pom.xml 自动扫描 + 手动配置兜底
- 发布风险从"上线后才发现"前移到"评审时预警"

## 场景 5: 单项目评审向后兼容

### 背景
`/local-review` 是已有核心功能，改造必须保证其功能、API、流程完全不变。同时，知识注入可能因分层改造而增强（自动获得产品线级知识），评审质量可能提升。

### 操作流程
1. 打开 `/local-review`，页面完全不变
2. 选项目、选分支、开始评审，流程不变
3. 核心链路 `buildLocalScanContext → classify → getKnowledgeForReview → batchReview → mergeReports` 全部保留
4. 知识注入可能更多：改造前仅 shared + 项目级知识，改造后额外注入 foundation + product 层知识

### 输出
- API 不变、报告格式不变、历史记录不变
- 不选产品线时，单项目评审的知识注入与改造前结果一致
- knowledge_entries 新增 scope_level 列默认 'project'，已有数据不受影响
- 所有现有 API 端点不删除、不修改签名，只新增端点

## 场景汇总

| 场景 | 改造前能力 | 改造后能力 | 关键提升 |
|------|-----------|-----------|----------|
| 多项目需求评审 | 手动 7-8 次单项目评审，人工汇总 | 1 次操作，自动扫描+并行评审+合并报告 | 操作次数 ↓87%，等待时间 ↓70% |
| 前后端联合评审 | 前后端分开评审，人工比对 API | 自动分组+跨技术栈检测 | API 不一致从"发现不了"到"自动标注" |
| 产品线管理/新项目接入 | 逐个手动添加，无知识继承 | 目录批量导入，自动继承 3 层共享知识 | 接入时间 ↓83%，首次评审知识覆盖 ↑12x |
| 依赖感知/公共组件改动 | 无依赖感知，发布后才发现不兼容 | pom 扫描+prompt 注入+报告标注下游 | 发布风险前移到评审时预警 |
| 单项目向后兼容 | 正常工作 | 正常工作，知识可能增强 | 零破坏性变更 |

### 关键指标

| 指标 | 改造前 | 改造后 | 幅度 |
|------|--------|--------|------|
| 需求评审操作次数 | 7-8 次 | 1 次 | ↓87% |
| 需求评审等待时间 | 21-24 min | 5-8 min | ↓70% |
| 跨项目问题发现 | 0% | 依赖配置决定 | 从无到有 |
| 新项目接入时间 | ~30 min/项目 | ~5 min（批量） | ↓83% |
| 新项目首次知识覆盖 | ~5% | ~60% | ↑12x |
| 合并评审知识加载量 | N x 全量 | 1 x 全量 + (N-1) x 项目级 | ↓60% |

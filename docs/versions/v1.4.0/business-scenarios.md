## 场景 D: 改动公共组件的接口

### 用户操作（改造后）

```
1. 在需求评审中，bpms-component 的 diff 包含:
   - ServiceFacade.java: login(String, String) → login(LoginRequest)
   - UserDTO.java: 新增 userNo 字段

2. 系统检测到依赖关系（pom.xml 扫描结果）:
   bpms-component → bpms-runtime (compile)
   bpms-component → do1cloud-form (compile)
   bpms-component → do1cloud-auth (compile)

3. LLM 评审 bpms-component 时，prompt 多了一段:
   "本次改动涉及 bpms-component 的公共 API。以下项目依赖此项目:
    bpms-runtime, do1cloud-form, do1cloud-auth。
    改动文件: ServiceFacade.java, UserDTO.java。
    请检查: 接口签名向后兼容、DTO 字段只增不删、是否需通知下游"

4. 报告中标注:
   [HIGH] ServiceFacade.login() 签名变更 — 破坏性变更
     文件: ServiceFacade.java
     跨项目影响: bpms-runtime, do1cloud-form, do1cloud-auth
     → 建议保留旧签名做 @Deprecated 过渡，或同步更新所有调用方

   [MEDIUM] UserDTO 新增 userNo 字段 — 向后兼容（新增不影响）
     文件: UserDTO.java
     跨项目影响: bpms-runtime, do1cloud-form
     → 下游项目如需使用新字段需同步更新，但不影响现有逻辑
```

### 对比现状

| 步骤 | 现状 | 改造后 |
|------|------|--------|
| 依赖关系 | 不知道谁依赖谁 | pom.xml 扫描 + 手动配置 |
| 接口兼容性 | LLM 不知道有下游 | prompt 注入依赖信息 |
| 问题标注 | 无跨项目标记 | 明确标注影响的下游项目 |
| 发布风险 | 发布后才发现 | 评审时预警 |

## 场景 E: 单项目评审（向后兼容）

### 用户操作（改造后）

```
1. 打开 /local-review（页面完全不变）

2. 选项目 bpms-runtime，选分支，开始评审

3. 评审流程完全不变:
   - buildLocalScanContext(repoPath, target, source) — 不变
   - classify(diffs) — 不变
   - getKnowledgeForReview({ project, productLine, techStack, ... }) — 签名变了但兼容
   - batch review — 不变
   - mergeReports — 不变
   - saveReviewRecord — 不变

4. 唯一区别: 知识注入可能多了产品线级知识
   - 改造前: shared 6 条 + java-backend 20 条 + bpms-runtime 项目知识
   - 改造后: foundation 18 条 + product 32 条 + bpms-runtime 项目知识
   - （知识更多了，评审质量可能提升）
```

### 对比现状

| 维度 | 现状 | 改造后 |
|------|------|--------|
| 页面 | 不变 | 不变 |
| API | `/api/review/local` | 不变 |
| 操作流程 | 不变 | 不变 |
| 知识注入 | shared + 项目级 | foundation + product + 项目级 |
| 报告格式 | ReviewReport | 不变（单项目不产出 RequirementReviewReport） |

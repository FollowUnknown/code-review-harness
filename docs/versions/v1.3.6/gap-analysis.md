> 日期: 2026-05-06
> 背景: 用真实 MR（do1cloud-form 聚合表去重 bugfix）对比架构师评审与 AI 评审

| # | 级别 | 核心发现 | 视角 |

| CR-002 | 中 | 去重只是"治标"，根因是维度查询返回重复记录，源头未治理 | 系统设计/根因分析 |

| # | 级别 | 核心发现 | 与架构师对比 |

- CR-003（注释风格）— 需对比文件内已有代码风格
- CR-004（可观测性）— 需理解生产运维需求

## 2. 差距根因

### 2.1 维度错配

**现象**：`do1cloud-form` 是 Java 后端项目，但 `getDimensionsForProject` 返回了 qiqiao 前端维度集。

**原因**：维度匹配逻辑是按 project 名做前缀匹配。`do1cloud-form` 在 `qiqiao/fore-end/` 下？不，实际是 `qiqiao/backend/do1cloud-form`。但维度集的 project 字段是 `qiqiao`，而传入的 project 是 `do1cloud-form`（从 MR URL 解析出的路径末段），无法匹配到 `qiqiao`，回退到默认 8 维。然后前端 seed 脚本注入了 qiqiao 维度集，但 local review 路由可能走了不同的 project 解析路径。

**根因**：缺少技术栈感知层。project 名到维度集的映射只靠字符串匹配，无法区分前端/后端。

### 2.2 知识库空白

**现象**：注入的知识全是 Vue 2 前端反模式（EventBus、v-html、$set...），对 Java 后端零参考。

**原因**：
- 种子脚本只建了 `shared`、`qiqiao`、`qixi` 三个知识库
- 没有 `java-backend` 或 `do1cloud-form` 知识库
- 知识召回是按 project 名过滤，`do1cloud-form` 匹配不到任何条目

**缺失的后端知识类型**：
- Java 集合性能约定（List vs Set vs Map）
- 后端可观测性规范（日志级别、关键路径 trace）
- 注释/代码风格约定
- 根因分析方法论
- Spring/BPMS 业务框架约定

### 2.3 评审视角单一

**现象**：AI 只发现 NPE 风险和测试覆盖，缺少性能、根因、可观测性视角。

**原因**：
- 维度集不包含这些视角（没有"数据结构选择"、"算法复杂度"、"可观测性"维度）
- 知识库没有引导 LLM 从这些角度思考
- Prompt 只有通用评审指令，没有后端工程专项指导

### 2.4 上下文不足

**现象**：架构师看到完整文件上下文做跨行关联分析，AI 只看 diff 片段。

**原因**：
- MR 评审模式下 AI 只拿到 git diff
- Local review 有 context-extractor，但 MR 路由没有
- `relatedFiles` 在 MR 路由中未启用

## 3. 知识库建设方案

### 3.1 短期：技术栈识别 + 后端维度集

**技术栈推断**：在 classifier 或 `getDimensionsForProject` 中加入基于文件扩展名的技术栈推断。

```
文件后缀统计:
  .java > 50% → Java 后端
  .vue > 50%  → Vue 前端
  .tsx/.jsx   → React 前端
  ...
```

**维度集**：

| 技术栈 | 维度集 | 维度 |
|--------|--------|------|
| Java 后端 | `java-backend` | 数据结构选择、异常处理、算法复杂度、并发安全、日志与可观测性、代码可维护性、根因分析、测试覆盖 |
| Vue 2 前端 | `qiqiao` | 安全、Vue 2 组件质量、Vuex 状态管理...（已有） |
| Vue 3 前端 | `qixi` | 安全、Vue 3 组件质量、TypeScript 类型安全...（已有） |

### 3.2 中期：后端知识库

按架构师评审模式建 3 类知识：

**反模式（AP-JAVA）**：
- `AP-JAVA-001`: `List.contains()` 用于频繁查找 → 应改 `Set`
- `AP-JAVA-002`: `Map.get().toString()` 无空值判断 → NPE 风险
- `AP-JAVA-003`: 条件跳过无日志 → 丢失可观测性
- `AP-JAVA-004`: 治标不治本的防御代码 → 应标注根因并计划源头治理
- `AP-JAVA-005`: 热路径字符串拼接 → 应使用 StringBuilder
- `AP-JAVA-006`: catch 块吞异常无日志 → 至少 log.warn

**约定（CONV-JAVA）**：
- `CONV-JAVA-001`: 注释风格统一 — "为什么"而非"做什么"
- `CONV-JAVA-002`: 关键路径必须有 log.debug 级别日志
- `CONV-JAVA-003`: 集合类型选择标准 — 查找用 Set，有序用 List，映射用 Map
- `CONV-JAVA-004`: 异常处理规范 — 受检异常必须处理，运行时异常防御性捕获

**经验（EXP-JAVA）**：
- `EXP-JAVA-001`: 聚合表场景 — 维度查询可能返回重复记录，源头去重优于消费端过滤
- `EXP-JAVA-002`: 乐观锁冲突 — 重复 ID 更新需要 Set 去重
- `EXP-JAVA-003`: 事务内批量操作 — O(n) 查找在批量场景下会成为瓶颈

### 3.3 长期：多维度评审架构

```
项目 → 技术栈识别 → 维度集 + 知识库
         ↓
  Java 后端 → java-backend 维度 + AP-JAVA / CONV-JAVA / EXP-JAVA
  Vue 2 前端 → qiqiao 维度 + QQ 反模式
  Vue 3 前端 → qixi 维度 + QX 反模式
```

需要改动的模块：
1. `classifier.ts` — 增加技术栈推断
2. `dimensions.ts` — 先按技术栈选维度集，再按 project 细分
3. `knowledge.ts` — 知识召回增加技术栈维度
4. 新增 `java-backend` 维度集和知识库种子

## 4. 评审评分标准（Java 后端维度）

### 数据结构选择
```
5分：集合类型完全匹配使用场景，查找用 Set、有序用 List、映射用 Map
4分：基本匹配，个别可优化
3分：存在不当选择但未影响核心性能
2分：核心路径使用了低效集合类型
1分：明显的性能反模式（如大批量 List.contains）
```

### 算法复杂度
```
5分：热路径均为 O(1) 或 O(log n)，无明显瓶颈
4分：大部分高效，个别 O(n) 可接受
3分：存在 O(n) 线性扫描但数据量可控
2分：核心路径有 O(n²) 或不必要的全量遍历
1分：性能严重问题（N+1、全表扫描等）
```

### 日志与可观测性
```
5分：关键路径有 trace，条件分支有 debug，异常有 error + 上下文
4分：主要路径有日志，个别遗漏
3分：有基础日志但不够全面
2分：关键路径无日志，排查困难
1分：几乎无任何可观测性手段
```

### 根因分析
```
5分：修复指向根因，附带源头治理方案
4分：修复有效且标注了根因位置
3分：修复有效但仅处理症状，未追溯根因
2分：修复方向正确但不完整
1分：修复偏离根因，可能引入新问题
```

# 知识库标签规范

## 概述

知识库中的条目按类型分类，每种类型代表不同层次和性质的知识。正确的类型标注有助于：

- 评审时精准注入相关知识
- 快速识别问题性质和严重程度
- 沉淀可复用的业务和技术资产

---

## 类型定义

### AP - Anti-Pattern（反模式）

**定义**：已验证的不良实践，必须避免。通常对应 CRITICAL/HIGH 级别的问题。

**特征**：
- 有明确的负面后果（性能、安全、可维护性）
- 有经过验证的修复方案
- 在特定上下文（语言、框架、业务场景）中成立

**示例**：
- Vue 2 模板中使用 `?.` 可选链（运行时语法错误）
- 在循环中进行同步数据库查询（性能问题）
- 明文存储用户密码（安全问题）

**字段**：
- `scope`: 适用范围（如"全局弹窗组件"、"Node.js 服务端代码"）
- `first_seen_in`: 首次发现的来源（如 "story-001100 + dialog.vue"）

---

### EXP - Experience（经验）

**定义**：从实践中总结的有用知识，帮助避免踩坑或提升效率。

**特征**：
- 来自真实项目经验
- 不一定有严重后果，但能提升效率或代码质量
- 可能是框架特性、调试技巧、工具使用等

**示例**：
- Vitest 中 `vi.mock` 的变量提升问题
- 使用 Chrome DevTools 的 Performance 面板分析长任务
- Git 的 `git bisect` 快速定位问题提交

**内容格式建议**：
```
场景：[具体场景描述]
建议：[具体操作建议]
```

---

### CONV - Convention（约定）

**定义**：团队或项目层面的编码规范、命名约定、目录结构等。

**特征**：
- 在项目或团队内保持一致即可
- 通常不涉及对错，关乎一致性
- 可能随项目演进调整

**示例**：
- 目录命名使用 kebab-case（`user-profile/` 而非 `userProfile/`）
- Vue 组件名必须多词（`UserCard` 而非 `Card`）
- API 响应统一使用 snake_case

---

### BN - Business Noun（业务名词）

**定义**：业务领域的关键概念、实体、配置项。

**特征**：
- 有明确的业务含义
- 有数据结构定义
- 可能关联多个业务规则

**示例**：
- 数据安全配置（`dataDisplayMode`, `dataMaskingConfig` 等字段）
- 订单状态（`pending`, `paid`, `shipped`, `completed`）
- 用户权限角色（`admin`, `editor`, `viewer`）

**字段**：
- `data_structure`: 数据结构定义（JSON 或伪代码格式）
- `default_value`: 默认值说明

---

### RULE - Business Rule（业务规则）

**定义**：与业务逻辑相关的约束、校验规则、处理逻辑。

**特征**：
- 通常依附于业务名词（BN）
- 描述"当 X 时，必须/应该/不能 Y"
- 可能有明确的推导来源

**示例**：
- 不配置权限时，所有人无可见权限
- 脱敏规则前后缀范围 0-N
- 订单金额超过 10000 元需要二级审批

**字段**：
- `derivation`: 规则推导来源（`代码推断`、`技术方案`、`需求文档`等）
- `parent_id`: 关联的业务名词（BN）ID

---

### TERM - Terminology（术语）

**定义**：技术或业务领域的专业词汇、缩写、概念解释。

**特征**：
- 帮助理解业务或技术上下文
- 可能是缩写、专有名词、行业术语

**示例**：
- 脱敏规则（Data Masking Rule）：对敏感数据进行掩码处理的配置规则
- QPS（Queries Per Second）：每秒查询数
- ROI（Return on Investment）：投资回报率

---

## 使用指南

### 选择类型的决策树

```
是否是不应该做的，有明确负面后果？
├── 是 → AP（反模式）
└── 否 → 是否有明确业务含义和数据结构？
    ├── 是 → BN（业务名词）
    │       └── 是否关联处理逻辑？
    │           └── 是 → RULE（业务规则）
    └── 否 → 是否是规范或约定？
        ├── 是 → CONV（约定）
        └── 否 → 是否来自实践经验？
            ├── 是 → EXP（经验）
            └── 否 → TERM（术语）
```

### 沉淀流程建议

1. **评审中发现问题** → 记录为 EXP（经验）或 AP（反模式）
2. **识别业务概念** → 沉淀为 BN（业务名词）
3. **提炼约束规则** → 关联 BN 创建 RULE（业务规则）
4. **持续迭代** → TEMP 状态的知识经过评审后 CONFIRMED

## 一、项目全貌

### 1.1 项目定位

CodeReview 是一个**基于 AI 的代码评审平台**，核心能力包括：

- 连接 GitLab MR，自动拉取代码变更
- 接入多 LLM Provider（DeepSeek、Anthropic）进行智能评审
- 风险分级、需求驱动评审、知识库沉淀
- 评审计划管理、批量评审、Markdown 报告导出
- 用户认证与权限管理

### 1.2 技术栈

| 层级 | 技术 |
|------|------|
| 前端 | React 18 + TypeScript + Tailwind CSS + Framer Motion |
| 后端 | Express 5 + TypeScript + better-sqlite3 |
| 构建 | Vite |
| 测试 | Vitest |
| AI | DeepSeek API / Anthropic Claude |

## 三、Harness 迭代过程

### 3.1 什么是 Harness

Harness 是**驱动 AI 按规范协作的框架**，不是业务功能。它定义：

- **怎么做事**：规划 → 开发 → 评审 → 提交的流程
- **怎么协作**：Planner / Generator / Evaluator 三个角色如何配合
- **怎么沉淀**：会话记录、Contract、知识如何保存和复用

### 3.2 五阶段演进

```
Phase 0: Baseline Rules
    |
    v
Phase 1: Session Superpower
    |
    v
Phase 2: Orchestration Superpower
    |
    v
Phase 3: Execution Superpower  ← 当前
    |
    v
Phase 4: Memory Superpower     ← 规划中 (v1.2.0)
    |
    v
Phase 5: Capability Superpower  ← 规划中 (v1.3.0-v1.4.0)
```

---

#### Phase 0: Baseline Rules (2026-04-22)

**问题**: 项目刚启动，没有任何约束，AI 可能做坏事情

**解决**: 建立三层防护

| 层 | 机制 | 作用 |
|----|------|------|
| 软约束 | `CLAUDE.md` | 每次对话自动加载，行为规范、红线提醒、自检清单 |
| 硬护栏 | `.claude/settings.local.json` | 系统级拦截，AI 无法绕过，禁止改密钥/生产配置 |
| 知识沉淀 | `docs/` | 隐性约定、架构、规范 |

**关键规则**:
- 改之前先说清楚（范围、原因、边界）
- 高风险路径专项审查（SQL、配置、密钥、权限）
- 隐性约定必须记录到 `docs/architecture/implicit-contracts.md`
- 禁止硬编码密钥

---

#### Phase 1: Session Superpower (2026-04-22~23)

**问题**: AI 对话是一次性的，跨天无法延续任务状态

**解决**: 建立会话机制

```
sessions/
├── active-tasks.md          # 跨天活跃任务汇总
├── YYYY-MM-DD.md            # 每日会话记录
└── 规则:
    ├── 对话开始时读 active-tasks.md
    ├── 关键节点实时追加记录
    └── 对话结束时生成总结
```

**效果**:
- 任意跨天任务都能从 `active-tasks.md` 恢复
- 每次会话都有总结，不丢失上下文
- 历史会话不污染当前上下文

---

#### Phase 2: Orchestration Superpower (2026-04-23~24)

**问题**: 不同任务走同一个流程，小需求被过度流程化，平台任务跳过架构设计

**解决**: 双轨编排 + Contract 状态机

**双轨分流**:

| 类型 | 场景 | 流程 |
|------|------|------|
| Business Task | 功能开发、bugfix、局部改造 | Planning → Development → Review → Commit |
| Platform Task | 架构设计、知识平台、运行时升级 | Contract → Architecture → Development → Evaluation → Knowledge Sync |

**Contract 状态机**:

```
draft → confirmed → in_progress → review_pending → completed
          ↑_______________|
```

**关键改进**:
- 任务先分类再进流程，不再一刀切
- Contract 不是文档而是阶段间唯一协议
- Platform Task 增加 Architecture 阶段（先设计再实现）
- Platform Task 增加 Knowledge Sync 阶段（通用结论回写 docs/）
- 每个阶段完成后 AI 主动暂停，等用户说"继续"

---

#### Phase 3: Execution Superpower (2026-04-28)

**问题**: 流程只是文档，没有执行证据，评审失败后无法自动修复

**解决**: 建立 Execution 证据层

```
sessions/execution/
├── runs/
│   └── {run-id}/
│       ├── plan.json            # RED: 计划阶段证据
│       ├── implementation.json  # GREEN: 实现阶段证据
│       ├── review.json          # IMPROVE: 评审阶段证据
│       └── artifacts/           # 产物文件
├── repairs/
│   └── {repair-id}/
│       ├── original-review.json # 原始评审结果
│       ├── fix-plan.json        # 修复计划
│       ├── verification.json    # 验证结果
│       └── retry-result.json    # 重试结果
└── checkpoints/
    └── {checkpoint-id}.json     # 阶段检查点
```

**自动触发规则**:

| 场景 | 自动写入 |
|------|---------|
| Contract 状态变更 | Checkpoint |
| 写/改代码 | Run 阶段记录 |
| 评审失败修复 | Repair 记录 |
| Agent 切换 | 更新 Run 阶段 |

**关键设计**: 预埋 Phase 4/5 字段
- `extractedForMemory` —— Phase 4 Memory 提取标记
- `extractedForKnowledge` —— Phase 4 Knowledge 提取标记
- `memoryLayer` —— Phase 4 记忆分层标记

---

#### Phase 4: Memory Superpower (规划中, v1.2.0)

**目标**: 从 Execution 数据中提取分层记忆，优化 AI 评审质量

**4 层记忆模型**:

| 层级 | 来源 | TTL | 内容 |
|------|------|-----|------|
| session memory | `sessions/YYYY-MM-DD.md` | 1天 | 当前会话临时状态 |
| task memory | `sessions/execution/runs/` | 7天 | 单次 Run 记录 |
| project memory | `docs/contracts/` + 历史 Run | 30天 | 项目规则、最佳实践 |
| validated knowledge | `sessions/execution/repairs/` | 永久 | 已确认的错误模式 |

**应用场景**:
- 开始新 Run → 召回 project memory → 注入项目规则到 Prompt
- 评审代码 → 召回 validated knowledge → 注入历史错误模式
- 修复问题 → 召回 task memory → 注入之前修复方案

---

#### Phase 5: Capability Superpower (规划中, v1.3.0-v1.4.0)

**目标**: Skill / Provider / Approval 的装配与治理

**v1.3.0 - 基础层**:
- Skill 注册与发现
- Provider 执行与治理
- Capability 依赖管理

**v1.4.0 - 增强层**:
- Skill 版本管理（多版本共存、灰度发布）
- Provider 智能路由（负载均衡、故障转移）
- Capability 依赖治理（依赖图、循环检测）

## 四、关键经验与教训

### 4.1 做得好的

1. **双轨编排**: Business Task / Platform Task 分流避免了"一刀切"问题
2. **Contract 驱动**: 每个任务有明确范围和验收标准，减少返工
3. **知识平台**: 从评审 Issue 直接创建知识，实现"评审即沉淀"
4. **Layered 架构**: Session → Orchestration → Execution → Memory → Capability 逐步推进，不跳跃
5. **预埋设计**: v1.1.0 的 Execution 记录已为 Phase 4/5 预留字段

### 4.2 需要改进的

1. **Hook 能力边界**: PreToolUse Hook 对 Write/Edit 的拦截能力未完全验证，当前靠审计日志兜底
2. **Execution 记录体积**: runs/repairs/checkpoints 可能快速增长，需要归档策略
3. **测试覆盖**: 部分 UI 组件和集成场景测试不足
4. **文档同步**: 多个 spec/plan 文档存在信息重复，需要统一维护

### 4.3 核心原则

> **Harness 负责定义"怎么做事"，CodeReview 负责定义"做什么事"**
>
> 两条线通过 Contract、Session、Review 和 Knowledge Sync 对接，不把业务概念固化进 Harness 核心。

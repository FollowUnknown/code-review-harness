# Sprint Contract: v1.2.0 Knowledge Precision Recall & Review Quality Improvement

> 日期: 2026-04-28
> 状态: completed
> 类型: Business Task
> 版本: v1.2.0
> **前置**: v1.1.5 (用户管理与 Knowledge 审核流程)
> **后置**: v1.2.5 (Harness 侧 Memory 系统)
> **预计工期**: 3 个迭代周期

---

## 1. 需求背景

当前 Knowledge 系统（v1.1.x）已实现基础 CRUD、6 层分层注入 (`getKnowledgeForReview`)、Prompt 格式化 (`buildKnowledgePrompt`)、自动提取 (`extractLearnings`) 和命中追踪 (`trackKnowledgeHits`)。但实际运行中存在以下问题：

- **召回粗放**: 仅按 `project` 名精确匹配，无代码模式/语义匹配，无关 Knowledge 注入噪声大
- **注入无优先级**: 6 层固定顺序 + 2000 行硬限制，高相关条目可能被截断
- **沉淀无质量**: 自动提取的 Knowledge 无置信度、无去重，重复创建相似 AP
- **生命周期缺失**: TEMP → CONFIRMED → DEPRECATED 全靠人工，无自动衰减/归档
- **质量不可量化**: 评审一致性、Knowledge 命中率、误报率无基线数据

本版本目标：**在不另建记忆系统的前提下，把现有 `knowledge_entries` + `buildKnowledgePrompt()` + `getKnowledgeForReview()` 做得更精准、更可量化。**

## 2. 范围定义

### 2.1 包含（In Scope）

**模块 1: Knowledge 精准召回**
- TASK-201: 代码模式匹配召回（AP.pattern 对变更文件列表匹配）
- TASK-202: 相关性评分 & 排序（项目匹配、代码模式匹配、严重度、命中率综合评分）
- TASK-203: Token 预算控制（替代 2000 行硬限制，低分条目截断）
- TASK-204: 命中反馈闭环（追踪 Knowledge 是否被采纳，更新 hit_count + confidence）

**模块 2: Knowledge 自动沉淀增强**
- TASK-205: 指纹去重（新增 `fingerprint` 字段，相似条目 MERGE）
- TASK-206: confidence 字段 & 计算（0-1 尺度，自动更新基于命中反馈）
- TASK-207: Knowledge 生命周期管理（TTL、自动 deprecate 低 confidence 条目）

**模块 3: 评审 Prompt 增强**
- TASK-208: 按相关性动态构建 Prompt（高 confidence + 高相关性优先注入）
- TASK-209: 变更文件路径精准匹配（BN/RULE/EXP 匹配变更文件路径，提升优先级）

**模块 4: 评审质量可量化**
- TASK-210: 评审一致性测试（选历史 MR 多次评审，计算一致性基线 > 85%）
- TASK-211: 质量仪表盘（一致性趋势、Knowledge 命中率、误报率、v1.1.x vs v1.2.0 对比）

### 2.2 不包含（Out of Scope）

| 项 | 说明 |
|----|------|
| Harness 侧 Memory 系统 | 由 v1.2.5 负责，本版本不碰 `sessions/memory/` |
| 语义相似度模型 | 不做 Embedding/向量检索，代码模式匹配作为 baseline |
| 多语言 Token 计数 | 先按字符数近似，精确 Token 计数后续迭代 |
| 知识图谱 | 关系表已有，不做图查询/可视化 |
| 自动修复建议 | 评审后自动改代码属于 v1.3.0+ 范畴 |
| MySQL 迁移 | 保持 SQLite，v2-platform-upgrade Phase 5 统一处理 |

### Phase 1: 核心召回 + 沉淀基础

**目标**: 建立精准召回和高质量沉淀的基础设施

**核心改动**:
- `getKnowledgeForReview()` 增加 `changedFiles: string[]` 参数，AP.pattern 做正则/子串匹配
- 新增 `scoreKnowledgeRelevance()` 评分函数（项目匹配 + 模式匹配 + 严重度 + hit_count）
- 替换 `KNOWLEDGE_LINE_LIMIT = 2000` 为 `KNOWLEDGE_TOKEN_BUDGET`（默认 4000 tokens，字符数近似）
- `knowledge_entries` 表新增 `fingerprint` (TEXT, INDEX) 和 `confidence` (REAL, DEFAULT 0.5)
- `extractLearnings()` 创建前查 fingerprint，相似则 MERGE（更新 content + hit_count）

**数据迁移**:
- 现有条目自动生成分 fingerprint（`type + project + title 标准化 + pattern`）
- confidence 默认值：已有 CONFIRMED 条目 = 0.7，TEMP = 0.3

**完成标准**:
- [x] 代码模式匹配生效，匹配到的 AP 优先级高于未匹配
- [x] 评分算法实现，排序结果经人工验证合理
- [x] Token 预算截断后 Prompt 仍完整可解析
- [x] 相同 fingerprint 不重复创建，MERGE 逻辑正确
- [x] confidence 字段和默认值正确
- [x] 所有现有 83+ 测试通过

### Phase 2: Prompt 增强 + 反馈闭环

**目标**: 让 Knowledge 注入更精准，建立反馈循环

**核心改动**:
- `buildKnowledgePrompt()` 改为按相关性评分排序构建，高 confidence 优先
- 注入内容标注来源 ID（`[id: AP-cw-001]`），便于追溯
- 评审流程中传入变更文件列表到 `getKnowledgeForReview()`
- BN/RULE/EXP 的 `module` 字段匹配变更文件路径，匹配到的提升优先级
- 新增 `review_knowledge_usage` 表扩展：`adopted` (BOOLEAN) 字段
- 评审完成后对比 issue 与 Knowledge 建议，标记是否采纳
- 采纳: confidence += 0.1（上限 1.0）；未采纳: confidence -= 0.05（下限 0.1）

**完成标准**:
- [x] 动态 Prompt 构建生效，注入内容可追溯
- [x] 文件路径匹配生效，匹配的 Knowledge 优先级提升
- [x] 命中反馈记录到 `review_knowledge_usage`，confidence 基于反馈更新
- [x] 前端展示 Knowledge 命中情况（ReviewResult 组件）

### Phase 3: 生命周期 + 质量量化

**目标**: 自动清理低质量 Knowledge，建立质量基线

**核心改动**:
- 新增 `last_verified_at` 字段
- 定时任务/手动触发：confidence < 0.2 且 30 天无命中 → 自动 DEPRECATED
- CONFIRMED 且 90 天无命中 → 标记 `review_status = 'pending'`（待验证）
- 提供 API: `POST /api/knowledge/:id/refresh` 手动刷新验证时间
- 选 3-5 个历史 MR，各评审 3 次，比较评分一致性（方差、排名相关性）
- 记录 baseline：一致性、Knowledge 命中率、误报率
- 前端新增 `/quality` 页面：展示趋势图、对比视图

**完成标准**:
- [x] 低 confidence 自动降级生效
- [x] 长期未命中标记待验证
- [x] 手动刷新操作可用
- [x] 评审一致性 > 85%
- [x] Knowledge 命中率 > 30%
- [x] 误报率 < 15%
- [x] 仪表盘数据正确，对比视图可用

## 4. 技术决策

| 决策项 | 选择 | 理由 |
|--------|------|------|
| Token 估算 | 字符数 / 4 近似 | 不引入 tiktoken 依赖，中文场景近似足够 |
| 代码模式匹配 | 正则/子串匹配 | 简单、可解释、无需 Embedding 模型 |
| fingerprint 生成 | type + project + title 标准化 + pattern | 稳定、可复现、无需哈希碰撞处理 |
| confidence 更新 | 固定步长（+0.1 / -0.05） | 简单可预测，避免复杂衰减公式 |
| 生命周期触发 | API 调用时检查 + 手动刷新 | 不引入定时任务库，减少依赖 |
| 一致性测试 | 历史 MR 回放 | 利用现有数据，无需构造测试集 |

## 5. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 代码模式匹配准确率低 | 中 | 先做精确匹配作为 baseline，模糊匹配做增量；匹配失败不降级，只影响排序 |
| Token 预算控制影响评审质量 | 中 | 保留行数限制作为 fallback（`max(KNOWLEDGE_TOKEN_BUDGET, lineLimit * avgCharsPerLine)`） |
| 指纹去重误合并 | 高 | MERGE 前人工确认（低 confidence 不自动合并）；保留 MERGE 历史 |
| 评审一致性测试数据不足 | 中 | 先用 3-5 个典型 MR，积累 baseline 后扩展；允许 80% 作为过渡期目标 |
| confidence 衰减过快/过慢 | 低 | 步长可配置（存 settings 表），上线后根据数据调参 |

## 9. 与 v1.2.5 的边界

| 职责 | v1.2.0（本版本） | v1.2.5（后续版本） |
|------|------------------|-------------------|
| 存储位置 | `knowledge_entries` 表 | `sessions/memory/` 文件系统 |
| 数据来源 | 评审结果（LLM 产出） | Execution 数据（Run/Repair/Checkpoint） |
| 核心能力 | 精准召回、自动沉淀、评审增强 | 3 层记忆、跨会话恢复、记忆升级 |
| 服务对象 | LLM 评审 MR | AI agent 编排 |
| 用户价值 | 评审更准、更一致 | AI 编排更智能、上下文不丢失 |

**两者完全独立，无数据桥接。**

# 代码评审质量提升设计

> 日期：2026-04-23
> 状态：draft
> 主题：基于当前 `codeReview + harness` 系统，如何持续提升代码评审质量

---

## 1. 问题定义

当前项目已经具备一套可运行的 AI 代码评审系统，包括：

- 文件风险分级
- 需求驱动评审
- 知识库积累
- 评审持久化与继续评审
- Review Plan 批量评审
- LLM 模块抽离与 Prompt 管理
- Harness 编排

因此，当前问题已经不是：

- 要不要继续加更多规则
- 要不要继续做更多页面
- 要不要继续接更多模型

而是：

**基于现有系统，如何把"能做代码评审"提升为"能持续提高代码评审质量"。**

---

## 2. 核心判断

### 2.1 不是继续堆规则

规则是必要的，但规则只是最低层约束，不等于评审质量本身。

如果只有规则，常见问题仍然存在：

- 本次评审判断对了，但下次不一定还能复现
- 发现了问题，但不知道为什么判断出来
- 同样的问题重复发生，但系统没有吸收经验
- Prompt 改了很多版，却无法证明效果是否更好

因此，下一阶段不应理解为"继续增加很多规则"，而应理解为：

**把规则、流程、证据、反馈闭环做成一个工程系统。**

### 2.2 对话有价值，但不是全部

对话能提升的主要是：

- 需求澄清
- 业务背景校准
- 用户对高风险判断的确认

但如果没有工程机制支撑，对话的价值会快速流失：

- 这次聊明白了，下次可能忘
- 这次校准了，但没有沉淀为通用知识
- 这次修复了，但没有形成可复盘的回环

所以：

- 对话是提质手段之一
- harness 工程才是让质量持续提升的底座

---

## 3. 当前系统已经具备什么

当前系统已经具备了成为"评审工程系统"的基础骨架：

### 3.1 风险感知

系统已经能按文件风险等级决定不同评审策略，而不是把所有改动一视同仁。

这意味着：

- 高风险代码可以投入更多上下文和更严格评审
- 低风险代码可以快速扫过，降低成本

### 3.2 需求感知

系统已经不只是看 diff，而是尝试理解：

- 这次变更要实现什么
- 是否真的按预期实现
- 代码和需求是否存在偏差

这意味着评审开始从"代码表面检查"走向"需求正确性检查"。

### 3.3 知识感知

系统已经开始从历史评审中提取知识，并在后续评审中回注。

这意味着系统已经不只是一次性判断器，而是在尝试形成评审记忆。

### 3.4 过程留痕

评审记录、LLM 调用日志、批量评审过程、Prompt 管理已经初步具备可追踪能力。

这意味着系统有条件进入下一步：

- 从"记录结果"
- 升级到"复盘过程"

---

## 4. 真正还缺什么

当前真正缺失的，不是更多零散功能，而是四类核心工程能力。

### 4.1 缺执行证据

现在已经有编排，但还没有统一回答这些问题：

- 这个阶段到底执行了什么
- 用了哪些输入
- 为什么得出这个结论
- 哪些验证命令证明了当前实现有效

如果没有执行证据，评审质量无法稳定提升，因为系统只能输出结果，无法输出过程。

### 4.2 缺修复回环

现在评审能指出问题，但还缺少正式的：

- review fail -> repair -> re-review

闭环协议。

没有回环，评审仍然更像一次性报告，而不是可纠偏的工程机制。

### 4.3 缺知识治理

现在知识库已经有了，但还没有真正解决：

- 什么知识可以自动写入
- 什么知识必须人工确认
- 什么知识已经过期
- 什么知识属于项目级，什么属于任务级

如果没有知识治理，知识库会越来越大，但不一定越来越有用。

### 4.4 缺效果验证

现在已经能改 Prompt、换 Provider、调策略，但还缺少验证机制：

- 哪种 Prompt 更有效
- 哪种策略误报更多
- 哪类问题经常漏掉
- 系统整体是否真的在变好

如果没有最小评测闭环，就无法判断系统是在进步还是在漂移。

---

## 5. 提升代码评审质量的正确方向

### 方向一：规则更清楚

规则仍然需要继续完善，但角色应降级为：

- 定义边界
- 定义红线
- 定义最低要求

而不是把全部质量问题都寄托在更多规则上。

### 方向二：流程更可靠

要把评审过程做成稳定流程，而不是一次次手工组织。

核心包括：

- 任务分流
- 阶段流转
- 用户确认停点
- 执行证据
- repair loop

### 方向三：知识更可信

知识库不是越多越好，而是越可信越好。

重点应放在：

- 作用域
- 来源
- 状态
- 写回规则
- 召回规则

### 方向四：系统会学习

高质量评审系统的关键，不是每次从零开始，而是能从历史中持续优化：

- 从历史 issue 中提炼模式
- 从误报中修正 Prompt 和策略
- 从修复闭环中反推评审标准

---

## 6. 基于现有系统，还需要做什么

### 6.1 先补 Execution Superpower

这是最优先的事情。

目标：

- 让评审不只是"输出报告"
- 而是留下完整执行证据链

需要补的内容：

- `Run`
- `StageRun`
- `Artifact`
- `VerificationResult`
- `ReviewDecision`

以及：

- Generator 阶段证据
- Evaluator 反馈格式
- repair loop 协议

### 6.2 推进 knowledge-platform

知识平台不是附属功能，而是提升评审质量的核心底座。

需要补的内容：

- `TEMP / CONFIRMED / DEPRECATED`
- Recall Policy
- Writeback Policy
- project / module / task 作用域
- 业务知识与框架知识边界

### 6.3 把 Prompt 从可编辑升级为可验证

当前 Prompt 已可配置，但还要继续补：

- Prompt Preview
- Prompt 渲染测试
- Prompt 修改后的结果验证

否则 Prompt 管理只是"可改"，还不是"可优化"。

### 6.4 补最小质量回归

用当前未完成任务建立最小回归闭环：

- Review Plan 测试补齐
- 前端组件测试补充
- 用户管理模块作为业务样本

目的不是追求测试数量，而是让关键评审链路有稳定回归保护。

### 6.5 最后再做 Capability 治理

在 Execution 和 Memory 稳定后，再推进：

- Provider Policy
- Capability Registry
- Approval / Sandbox 边界

否则会过早抽象，增加系统复杂度。

### 7.2 可延后处理的任务

| 任务 | 原因 |
|------|------|
| `TASK-002` OpenCodeServer 第二期 | 更适合作为 Capability Phase 的验证场 |
| MySQL 迁移 | 不直接提升评审质量，属于底层替换 |

---

## 8. 推荐行动顺序

### 第一阶段

- 补 `Execution Superpower` spec
- 升级 Generator / Evaluator 规范
- 建立阶段证据和 repair loop

### 第二阶段

- 推进 `knowledge-platform`
- 抽象 Memory Superpower

### 第三阶段

- 完成 Prompt Preview
- 补 Prompt 和 Plan 的关键测试

### 第四阶段

- 用业务任务验证整套链路
- 再考虑 Capability Registry 和 Provider Policy

---

## 9. 一句话结论

对于当前项目而言：

- 不应该把下一步理解成"继续加很多规则"
- 也不应该把提升质量完全寄托在"多和系统对话"

真正要做的是：

**基于现有系统，补齐执行证据、修复回环、知识治理和效果验证，让代码评审从功能能力升级为持续改进的工程系统。**
